## 1. 结论与证据边界

可以进入有限的工程准备，但尚不能把现有任务清单直接视为可执行、可验收的开发合同。

仓库目前只有上述文档与 `.gitignore`，没有应用、规则集、契约、迁移、CI 或测试文件；审查开始时工作区干净。因此 README 中的 `make` 命令是目标形态，文档中的版本核实、用户验证与质量能力声明均不能视为本次运行证据。

产品主线明确：证据 → 规则评估 → 人审 → 确定性报告 → 整改 → 复测。主要缺口集中在范围冲突、状态与评分语义、版本快照、任务恢复，以及验证工作的排期。建议保留技术栈决策，先补这些契约，避免在实现中各自猜测。

下表中的“建议”是待落地方案，不代表 Product Owner 已批准修改 PRD。执行顺序见 [详细执行方案](05_EXECUTION_PLAN_v0.1.md)。

## 3. 内容与事实声明的处理

- TECH_SPEC §3、工程规范 §2、ADVICE §1/U-5 包含精确版本、发布日期与安全公告结论。本次只确认这些文字存在，没有独立核验；建立运行环境时须访问官方 release/security 信息并留下 URL、核对时间、实际安装版本和锁文件，不直接复制“已核实”。
- ADVICE 的“评审一眼看穿网图”“素材版权问题”等概括不作为排期依据。工程 fixture 可自制，真实验收集需要来源、使用授权和场景真实性；具体法律适用未在本次审查中判断。
- 工程规范 §5.2 的“加规则零代码改动”只对现有 evaluation_type、证据类型和评分表达能力内的新规则成立。新增能力仍需代码/契约变更，不能用绝对表述否定必要工程工作。
- PRD §22 将采购意向、续用、转介绍也列入 E4；它们不能自动表述为真实付费。验证记录应分别存事件、行为、付款证据和判断，不只保留一个 E 等级。
- PRD §28 要求 Evidence Log，但仓库尚无实际记录载体；应建立脱敏索引和访谈模板。仓库未找到记录不等于线下从未访谈。

保留 Next.js + Go + Python + PostgreSQL 的既有 D-003，不借审查扩大为架构重选；保留 JSON Schema、Evidence grounding、人工确认、确定性评分及 run 版本化。Redis、pgvector、队列平台和 Guest Layer 继续按真实需要引入。
